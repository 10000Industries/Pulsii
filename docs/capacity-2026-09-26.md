# Capacity evidence — 26 September 2026

Production ceiling: 1,000 WebSocket connections on one $7/month 0.5 CPU/512 MB
instance. This replaces the trial's 20-connection setting. It is a configured
ceiling supported by the tests below, not a universal smoothness guarantee.

## Runtime change

Encode each pulse batch once. Index sender-owned records once, then copy byte
spans to exclude their own echoes. This avoids validating, quantizing and
encoding the same pulses again for every sender. Original client appearance,
touch handling, immediate local response, pulse order and binary format stay
the same. An exhaustive subset test checks byte-for-byte exclusion equivalence;
all 59 tests pass.

Settings: connection limit 1,000; join burst 200 and refill 50/second; HTTP burst
3,000 and refill 500/second; pulse burst 1,500 and refill 500/second across the
whole canvas; candidate queue 2,048; batches up to 1,024 every 50 ms. The high
per-client pulse allowance is unchanged. Limits remain to contain overload.

## Measurements

Each run used 1,000 clients with the browser's immediate protocol, one burst
pulse from every client, then 8,000 further pulses shared among all senders.
Every client checked unique peer receipt, excluding its own echoes.

| Check | Local optimized | Render isolated optimized |
| --- | ---: | ---: |
| Connected clients throughout | 1,000 | 1,000 |
| Pulses sent | 9,000 | 9,000 |
| Expected/received peer records | 8,991,000 / 8,991,000 | 8,991,000 / 8,991,000 |
| Missing/duplicate records, busy notices, disconnects | 0 | 0 |
| Sustained sending duration | 20.016 s | 75.897 s |
| Actual sustained aggregate input | ~400/s | ~105/s |
| Receive latency p50 / p95 / p99 | 43 / 204 / 264 ms | 500 / 3,191 / 4,489 ms |

The hosted run used Free compute measured by Render at 0.15 CPU and 512 MB.
The generator and server competed for that same allowance. Server RSS was
about 91 MB at the end. Production has 0.5 CPU and does not run the generator,
so more headroom is a reasonable inference, not a measured production result.
The hosted 400/s timing target was NOT met; the delivery/connection check was.
Neither run measures canvas painting on physical phones/tablets or long soaks.

Before optimization, the same hosted workload rejected 4,928 of 9,000 pulses,
with approximately 10-second server event-loop stalls. After optimization it
accepted/delivered every pulse. Target server commit: ae3b94f0abb15d9970243a25f4f027d0fbb6a7be.

The original external test attempt was inconclusive: it reached a peak of
235 accepted connections with zero app-side rejection, then encountered proxy
403/502 errors before sending pulses. The completed hosted test ran over
loopback, not through Render's public edge. No synthetic crowd was sent to the
public canvas. The temporary review start command must be restored and the
review service suspended after testing.

## Cost and next boundary

The connection setting does not change the fixed compute price. Every shared
pulse travels to each connected peer, so sustained crowds increase bandwidth.
At 1,000 recipients and 400 pulses/second, roughly 11.4 GB/hour of batched pulse
payload is possible, before HTTP/TLS/control overhead. Render Hobby includes
5 GB/month shared by the workspace, then $0.15/GB public outbound traffic:
https://render.com/docs/outbound-bandwidth

Thus the earlier approximate £6.40 base-hosting estimate cannot be treated as a
£7 total guarantee for a continuously busy crowd. No paid tier, instance count,
workspace plan, autoscaling, or extra paid service is added by this change.
Observe real CPU, memory, rejected pulses, event-loop delay, and bandwidth
before increasing the ceiling further. A crowd-on-device test remains useful
before claiming responsiveness at heavy simultaneous tapping rates.
